# 方案 B：站点多语种的真实缺口与推进计划（2026-10-17 实测）

本文所有数字都是**跑出来的**，不是估计。测量脚本：`infra/ld_i18n_measure.py`（页面渲染态）
与 `infra/ld_dict_dump.js` / `infra/ld_gap_list.js`（词典真值，按生产脚本顺序加载）。

## 一、词典覆盖率（551 条中文原文）

| 语种 | 已覆盖 | 说明 |
|---|---|---|
| en | 551 / 551（100%） | 兜底语言，全覆盖 |
| es / pt / id / vi | 465 / 551（84%） | 真翻译，按实测矿工来源地选的语言 |
| fr de ru ja ko ar hi tr fil | **55 / 551（10%）** | 基本没译 |

**结论：语言下拉里列着 15 种，其中 9 种实际给用户看的是英文。**
因为 `?lang` 未命中时回退英文（10-16 修的 `LD-I18N-FALLBACK`），所以页面不显中文、
看起来"正常"，但下拉上写着 Deutsch / 日本語 / 한국어 / العربية，点进去是英文。

## 二、缺口分三类，处理方式完全不同（混做就白干）

1. **静态散文**（funds、nodes、institutions 等）：词典按"中文整句精确匹配"能命中 → 加词条即可。
2. **运行时拼接串**（治理页的 `赞成 100%(1人) · 反对 0%(0人) · 弃权 0% · 46h 后截止`、
   按钮 赞成/反对/弃权/执行）：数字每次都变，词典永远命中不了 → **必须改代码里的标签表**。
   ✅ 已做（v1.9.2）：`governance_2.js` 加 `GOVL` 标签表，覆盖 zh/en/es/pt/id/vi，其余英文兜底。
   实测治理页汉字占比 10.9% → **2.3–2.7%**，中文态不受影响。
3. **被行内标签切断的半句**（funds 页 87 段里一大半，如"…是唯一可以当作"现在"的部分；下面标了"
   ＋下一段"的表格是 2026-10-14 手工核对…"）：逐段塞词典会拼出语法破碎的机器味英文，
   **比诚实显示中文更糟** → 需要把段落重排成"整句可译单元"，属编辑性重写。

另有两类**不算缺口**、但曾被我的量具误计：语言下拉里各语种的自称（`中文`、`日本語`
本就该用本民族文字显示）、以及命令行示例里的 `<地址>`（代码块，不译）。

## 三、我自己那道语种门禁的盲区（必须记下来）

`ld_render_all.py` 的语种棘轮只量"英文页里还有多少汉字"。它**看不见**"下拉里承诺德语、
实际给的是英文"这种情况——因为英文页没有汉字，指标是绿的。
所以：绿灯不等于没问题，只是没问题的那一维。
待补的检查（下一步做）：对每个下拉里列出的语种，抽样比对渲染文本里该语种的特征词占比，
覆盖率低于阈值就在门禁输出里点名（先报告、不阻断，避免把产品决策变成红色噪声）。

## 四、下一步（按性价比排序）

1. **要么把下拉收成"真翻译的 6 种 + English"，要么补齐那 9 种**——这是产品取舍，
   需要所有者定：留着 15 种是"看起来国际化"，收齐是"不承诺做不到的事"。
   我的建议：**先收**（改成 6 种真译 + 英文），成本近零、且消除误导；等真实流量证明
   某个语种有价值再补。
2. funds 页整句重排 + 词条（87 段，约 2300 汉字），一次一页，做完就把该页纳入语种棘轮。
3. institutions（97 段 / 1983 字）、app（58 段 / 1131 字）随后。
4. whitepaper 719 段 / 3.8 万字符：这是整本白皮书，不该走"逐段塞词典"的路子，
   建议改为**单独出英文文档**（一份 `whitepaper_en.md`），而不是把 3.8 万字拆成碎片机翻。
