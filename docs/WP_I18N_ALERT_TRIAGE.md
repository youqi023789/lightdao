# WP-I18N 16 条告警分诊（2026-11-06T22:00Z 实测）

> 触发面：`ld_wp_check.py`（root cron `40 * * * *`，日志 `/home/ubuntu/ld_wp_check.log`）。
> 每轮固定输出「WP-I18N 共 16 条告警」，其中 13 条措辞为「清单里 `<语种>` 的成功段数为 0，但文件存在（数字与事实矛盾）」。
> 本文回答一件事：这 16 条里哪些是生产问题，哪些是判据自己写错了。**结论：13 条是判据 bug，3 条是真问题。**

## 1. 一句话结论

判据读了一个清单里**从来不存在**的字段 `ok_lines`，取默认值 0 就断言「数字与事实矛盾」，于是 13 个语种全被判为异常；真正的缺口只有 hi / ar / ru 三个语种译文没做完（另有 895 片段暂留原文）。文件和站点内容本身是好的。

## 2. 判据侧证据（13 条 = 误报）

检查逻辑（`ld_wp_check.py:92-95`）：

```python
for l in LANGS:
    rec = man.get(l)
    if rec and int(rec.get("ok_lines", 0)) == 0:
        alert("清单里 %s 的成功段数为 0，但文件存在（数字与事实矛盾）" % l, alarms)
```

而生成方写出的清单 `/home/ubuntu/ld_wp_manifest.json` 每个语种的实际键集合，13 个语种完全一致：

```
{bytes, cached, kept_zh, pending, src_sha, stopped_early, ts, units}
```

- 没有 `ok_lines`，也没有 `bad_lines`。
- 全仓 + 网关全局检索 `ok_lines`：只有上面这一行**读**它的地方，没有任何一处**写**它（`grep -rn ok_lines` 只命中检查器）。
- `git log -S"ok_lines" --all`：唯一命中是把该检查器入库的那次提交（`e90002e chore(infra): 7 个 cron 在用脚本入库`），说明这个字段名从入库第一天起就对不上生成方，不是后来改名改丢的。

所以：`rec.get("ok_lines", 0)` 恒为 0 → 只要清单有这个语种记录就必报警。13 个语种 → 13 条，恒定复现，与白皮书内容质量无关。

同一处还有第二个死字段读取（`ld_wp_check.py:87-89`）：

```python
tot_bad = sum(int(man.get(l, {}).get("bad_lines", 0)) for l in LANGS)
print("清单：%d 个语种，结构校验失败并保留原文共 %d 段" % (len(man), tot_bad))
```

`bad_lines` 同样不存在 → 永远打印「保留原文共 0 段」，把真实数字（895 段）压成了 0。这行是 `print` 不是 `alert`，所以不报警，但它让运维看日志时误以为没有残留。**这一条比 13 条误报更有害**：它把真问题的量级隐藏了。

真实对应字段是 `kept_zh`（保留中文原文的段数）与 `pending`（还没翻的段数）——本轮两者完全相等（各 895），说明「保留原文」全部来自「还没轮到翻译/翻译没返回」，而不是「翻完了但结构校验挂了被退回」。后者才是判据文案里说的「结构校验失败被保留原文」，与事实不符。

## 3. 生产侧证据（3 条 = 真问题）

按 `kept_zh / units`（每语种 343 段）统计，本轮清单：

| 语种 | units | kept_zh | 保留原文比例 | 检查器报的中文行比例 | 判定 |
|---|---|---|---|---|---|
| hi | 343 | 272 | 79% | 69% | 真问题 |
| ar | 343 | 209 | 61% | 37% | 真问题 |
| ru | 343 | 148 | 43% | 29% | 真问题 |
| tr / ja | 343 | 32 | 9% | 未过阈值 | 正常 |
| de | 343 | 32 | 9% | 未过阈值 | 正常 |
| vi | 343 | 27 | 8% | 未过阈值 | 正常 |
| 其余 6 语种 | 343 | ≤32 | ≤9% | 未过阈值 | 正常 |

两条独立量具（清单计数 vs 全文中文行占比）方向一致、数量级一致 → 这 3 条是真信号，不是判据误差。合计 `pending=kept_zh=895` 段、`cached=3495/4459`（78% 已缓存）。`stopped_early` 全为 false，说明不是被限流中途截停，而是这三个语种 MT 回包切分反复失败退回逐条后仍没做完（同一时段 `ld_alerts.log` 里 `I18N-MT2 WARN 回包切分不等` 集中出现在 hi/tr/fil/es/pt/id/vi，与上表的重叠方向一致）。

一处需要留意的判据弱点：告警举的「例证行」取的是 `bad[0]`，本轮命中 `[中文原文 / Chinese original](/whitepaper.md)` —— 这是每个译文中英双语并存的固定导航链接，**任何**译文都会命中，属于分母噪声，会轻微抬高比例。它不足以解释 79%/61%/43% 的量级，所以结论不变，但阈值口径以后应把该链接行排除。`ja/ko` 已在 `CJK_HEAVY` 白名单里豁免，处理正确。

## 4. 为什么本次没有直接改脚本

- 检查器是 root cron 在用的生产脚本，且已在 `infra/` 有仓库镜像；就地手改会立刻让 `ld_gate_watch.py` 报 `deploy gates drifted`（本日 04:09Z 就有一条 `promote.py` 的同类漂移记录，后续两轮已回到 drift=0）。
- 属于「判据要不要重写」的口径决策，不是无争议修复：改成读 `kept_zh` 会让原本静默的 `tot_bad` 行暴露出 895 这个数，可能把当前的 16 条误报换成 3+1 条真告警的**新基线**，需要人工确认阈值。
- 按自走规则「任何不确定只报告不动手」，本文只定位根因并给出待批修法，不动线上。

## 5. 建议修法（待人工批准，二选一即可，均为读侧改动）

1. 最小修：`ok_lines` → `kept_zh`，判据从「成功段数=0 即矛盾」改成「`kept_zh == units` 即整篇没翻动才矛盾」；同时 `bad_lines` → `kept_zh`，让「保留原文共 N 段」显示真实量级。
2. 稳一点：删掉 13 条死字段告警，改为在清单里新增 `schema_version` 字段，检查器读不到约定版本就报「清单与生成方版本不匹配」一条，避免以后再出现字段改名导致的静默失真。

改完必须用 `ld_wp_check.py selftest`（内置 5 类故障注入，要求 5/5 被抓到）回归，再观察一轮 `40 * * * *` 的输出条数。
