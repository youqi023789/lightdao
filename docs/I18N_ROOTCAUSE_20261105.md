# 多语言今天到底卡在哪 · 2026-11-05 根因与修法（全部真机实测）

页面残留中文从"每个语种 2,608 处"降到个位数，靠的不是多补译文，而是查出**四个结构性故障**——
译文早就在缓存里，是投递链路把它吃掉了。按"发现方式 → 证据 → 修法 → 怎么证明修好了"记录。

## 故障 1：机器表用"只填空槽"的展开器登记，新句子全成死行

- 证据：`funds.html?lang=de` 真机仍有 82 个中文文本节点，逐条查 `window.LDI18N[整句]` →
  **82/82 都是"词典里没这个键"**，0 条是"有键但缺德语"；而缓存 `ld_i18n_mt_cache.json` 里这些句子都有 14 语译文。
- 原因：`__ldExpandLangs(L,T)` 的语义是"只往**已存在**的键里填空语种"（`if (!dict[zh][langs[k]] && parts[k])`），
  它不会创建键。11-04 我把机器表从"自己建键"改成"与人工表同构 + 调展开器"时，正好把建键能力改丢了，
  于是每一轮机器翻译都白做。
- 修法：`rewrite_mt_table.py` 在调展开器**之前**先为"词典里完全没有的键"建条目（人工已有的键绝不覆盖）。
  计数写入 `window.__ldMtCreated`，让"它真的干活了"可被外部看到。
- 验证：修后 `institutions/nodes/funds` 的每语种残留从 17~51 掉到 1~5；`__ldMtCreated` 在真机读数里非零。

## 故障 2：磁盘上有 8 片机器表，页面只挂 5 片

- 证据：`institutions.html?lang=de` 上 `window.__ldMtKeys = 1`（最后加载那片只有 1 行），
  而磁盘 `i18n_mt_1..8.js` 共 303 行；页面 `<script>` 列表只有 1..5。
- 原因：分片数按体积切，缓存一涨片数就变；`wire_mt_shards.py` 只重写**仓库**页面，
  线上页面的引用块要等 promote 才更新——中间那段时间线上就是"少挂两片"，而所有门禁全绿。
- 修法：新增 **g13 发布门禁**（`ld_i18n_wiring.py`）：磁盘上的每一个 `i18n_mt_*.js`
  必须被每个页面按序引用，多挂/少挂/顺序错都算失败；promote 不过。
- 反向验证：在临时目录里人为删掉两页的一片引用 → 门禁必须变红（实测报
  `funds.html：少引用 i18n_mt_7.js（应有 7 片，实际 6 片）`），确认它不是摆设。

## 故障 3：每页各挂一串词典，同一句在这页有译文、在那页没有

- 证据：`navFallback=8`、`__ldTgaps` 里 8 条 `de|首页`…；对比发现 `audit_logic/blog/…` 少挂 `i18n_pages_en3.js`。
- 原因：18 个页面的 i18n `<script>` 清单是各时期手工攒出来的，彼此不一致 → 典型的"同一事实多份表达"。
- 修法：`normalize_i18n_blocks.py` 把所有页面统一成同一份清单与顺序；
  顺序由**唯一一处**定义 `ld_i18n_order.py`（i18n.js → core → pages_en* → **i18n_lat.js（展开器本体）**
  → 其余人工表 → 机器表最后）。g13 也 import 同一函数，避免"页面按 A 顺序写、门禁按 B 顺序判"。
- 附带修掉的两个坑：
  - `i18n_lat.js` 必须排在表式批次之前，否则表尾巴拿到 `expander-missing` 直接 return（9 语一列都不灌）；
    表式文件现在还有一条兜底：展开器没定义时先登记进 `__ldTables`，boot 时统一展开。
  - `navT()` 的二次运行假缺口：切语种后节点文本已是德语，再拿德语去问词典 → 记成硬缺口
    （把指标弄脏，真漏 15 条也看不出）。改成"只对含汉字的文本问词典"。

## 故障 4：查表两边口径不一致（节点内部换行）

- 证据：`nodes.html?lang=de` 剩 8 个中文节点，其中「(LIGHT,权益绑定;作恶或长期离线将被 slashing 罚没)。」
  整句已在缓存里；采集端把 `\s+` 压成一个空格，运行端只做 `raw.trim()` → 键对不上。
- 修法：`i18n.js` 查不到时再按"折叠空白"的键查一次（原样键优先，老条目不受影响）；
  属性（title/placeholder/aria-label）同口径。
- 附带：「中文 / English」这类刻意并列标签，整串查不到时改为**只把英文那半换成本语种**，
  且必须"中文键与它的 en 值同时等于两半边"才替换（避免 `Back` 一词多义串味，这坑踩过）。

## 长文档不能靠词典：白皮书改走整篇文件

`whitepaper.html` 是 fetch `/whitepaper.md`（84,499 字节 / 1,147 行）后现渲染的。
整篇文档每个语种 2,608 处中文，逐句进词典要几万条键，页面体积也扛不住。
现在按语种生成 `/wp/whitepaper.<lang>.md`（`ld_wp_build.py`），页面按语种取文件：

- 结构保真：代码块整块不译；每段译文校验行数/`|`/`](`/反引号/`#`/列表项计数，
  不一致先单独重译，仍不一致就**保留中文原文并计入 `kept_zh`**（宁可留原文，绝不把表格链接翻坏）；
- 限流退避：429 走 5/15/45/120 秒退避，连续失败就停手，把剩余段记成 `pending`（不假装完成）；
- 断点续跑：每语种一份单元缓存，原子写盘；cron 每小时续一次；
- 诚实声明：文件头人工写一行"机器翻译、未经人工校对、以中文原文为准"（不用机翻写声明）；
- 防"拿回首页当白皮书"：nginx 的 `try_files` 对缺失文件返回 200 + index.html，
  所以前端必须验内容形状（长度 + 不以 `<!DOCTYPE`/`<html` 开头 + 头部无 `<script>`），否则退回中文原文并明写提示；
- 门禁 `ld_wp_check.py`：13 语种文件在不在（站点与仓库两份且必须一致）、体积、中文行占比、
  声明行还在不在、前端是否仍按 `/wp/` 取。`--selftest` 植入五种坏法，实测 5/5 报警。

## 机器翻译后端：卡死三批的真原因是后端选错

- 证据：03:30~06:00 三批 cron 全部 `0 成功 / 45 失败`，错误码 `HTTP 429`（MyMemory）；
  同一时刻真测 google gtx：连发 12 次 12 成，zh→en/de、en→ja 都对。
- 修法：`ld_i18n_mt_build2.py` 改 **gtx 优先、MyMemory 兜底**，逐语种记账可续跑、
  同语种多条打包成一个请求（长文档才是分钟级）、`flock` 防并发互踩缓存。
- 自检：流水线自己写 `ld_i18n_mt_state.json`，看门狗 `ld_i18n_mt_watch.py` 每小时判
  "还剩几条 + 距最后一次成功多久"，超 90 分钟报警。反向验证：植入 91 分钟前的假成功时间戳
  → 必须非零（实测抓到），否则就是"流水线停了和补完了看起来一模一样"。

## 复测口径本身也修了三处（量具错比没量更危险）

1. 语种表漏了 `ja`（14 语种只测 13 个）→ 日语坏了没人发现；补齐。
2. 日语/韩语译文本身含汉字，早期当成漏翻 → 日语页永远"没修好"。改为先渲染中文版取"源串清单"，
   只有和源串一模一样的算真漏翻；译文里夹带汉字单列"夹生"，只参考不判失败。
3. 中英并列块（旁边挂着英文对照）被算成漏翻，数字虚高几百条；单列"中英并列"计数，不混进真漏翻。

## 收尾时（v1.10.33）的实测数字与还剩下的事

真机普查（每页 × 该语种渲染后取词计数）：
- `de`：全部页面真漏翻 0、静默显英文 0；白皮书语种文件已有（97% 译文，个别表格段保留原文并计数）。
- `ja`：index/landing 各 2 处片段、nodes/governance/funds/institutions 0；运行时取词缺口从 7 归 0。
- 白皮书 13 个语种的整篇文件都已生成到线上，其中 ar/hi/ru 等仍有几百段"结构校验没过→保留原文"
  （`ld_wp_manifest.json` 里逐语种记 `pending/kept_zh`），keeper 与每小时 cron 会继续啃。

这一轮又抓到并修掉的三个"指标被弄脏"的问题（都不改变显示，只影响我们能不能发现真问题）：
1. **navT 拿日语译文去问中文键**：i18n 应用后导航二次重跑，节点已是「採掘/検索」，
   含汉字 → 通过"只问含汉字的文本"防护 → 词典必然查不到 → `__ldTgaps` 白记 7 条。
   改成导航直读词典（不计缺口），要看没翻到就盯 `__ldNavFallback`（它才是"退回英文小表"的真相）。
2. **普查把正常日语/韩语当漏翻**：判据改为"节点里出现假名/谚文即视为已是日韩文"，
   单列"日韩正常译文节点"计数，不改口说"零问题"，只是不再把它算成故障。
3. **人工词典里夹简体字**：`i18n_b3.js` 两处（上传済み→アップロード済み、长时间→長時間）。
   新增独立检测 `g12_simp_check.py`（每小时 cron + 可单独跑），字表刻意排除
   "日语新字体同形"的字（当点断式争律）——第一版把这些列进来，16 条告警 12 条是误杀。

一句话教训：这次多数问题不是"没译"，而是**译文在链路上被吃掉**或**量具自己看错**。
所以每一条修复都配了"能被复现的证据"和"植入故障必须报警"的反向验证。
