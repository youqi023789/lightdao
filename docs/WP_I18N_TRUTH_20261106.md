## 4. 三个判据缺陷（这次刷屏的根因在这里，不是翻译突然坏了）

- **D1｜`ok_lines` 字段不存在**：检查器第 5 项用 `rec.get("ok_lines", 0) == 0` 判"清单在骗人"，但生成器写出的清单只有 `src_sha/units/cached/pending/kept_zh/bytes/stopped_early/ts`，**从来没有 `ok_lines`**。于是每个语种恒定命中 → 每天刷 13 条假阳性。真正该读的字段是 `kept_zh`。
- **D2｜`bad_lines` 字段不存在**：第 6 项「manifest 里 bad_lines 总数与文件实况一致」同样读一个不存在的键（实测 `grep -c bad_lines` = 0），`tot_bad` 恒为 0 → **这一条检查名存实亡**，永远绿，也永远抓不到任何东西。
- **D3｜en 不在流水线语种表里**：`LD_WP_LANGS` 与 `LANGS` 都不含 en，所以英文白皮书**在构建、检查、清单三条环节结构性不存在**——它不会被判"缺"，也永远不会被补。目前靠 `client/js/whitepaper_2.js` 的 `FB.en` 兜底，给英文用户显式提示「暂无本语种译文，以下为中文原文」，这点符合 §11.1「透明优于完美」，**但兜底不是履约**。

**已核实为"不是缺陷"的一项**（避免下次误修）：检查器用 `CJK_HEAVY = {"ja","ko"}` 豁免了中日韩——日语译文里汉字是正常书写，拿 25% 汉字行阈值判 ja 会假阳性，这个坑**已经有人填了**，不需要动。

## 5. 真问题（判据修好之后仍然存在的问题）

`hi / ar / ru` 三份文件**存在**，所以加载器认为该语种"有译文"，不降级、不挂"暂无译文"提示，直接把 79%/61%/43% 仍是中文的内容当作成品呈现给读者。这不是账面问题，是**显示≠真相**：违反白皮书 §11.4 的读者预期，也与项目自身「可领取=链上真相 / 显示==真相」的 QA 口径冲突。
