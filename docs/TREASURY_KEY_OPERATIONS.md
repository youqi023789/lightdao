# 金库签名钥运行手册（TREASURY KEY OPERATIONS）

生效时间：2026-10-16 01:37 UTC（北京 09:37）。本文件记录一次**主动降低集中风险**的变更，
以及今后动用金库时的正确流程。

## 变更内容

网关服务器上**不再持有**金库 5 个签名人的私钥。

- 摘除前：`~/.wasmd/keyring-test/signer1..signer5.info`（明文，Cosmos `test` 钥匙串 = 私钥直接落盘）
  → 任何人拿到这台机器，就凑齐 3/5 票，可绕过审批发起并执行金库转账。
- 摘除后：5 把私钥只存在于**加密冷备份**中；解密口令**只由所有者离线保管**，服务器上没有。
- 与密文同机存放的口令文件已一并清除（否则"加密"形同虚设：拿到机器就能自己解）。

链上安全机制**未改动**：仍是 3/5 多签审批 + 72 小时时间锁。变的只是"攻击者需要拿下的东西"
从「一台服务器」变成「一台服务器 + 一份离线口令」。

## 摘除前的强制闸门（已执行，通过）

1. 从加密备份解密到临时目录，逐把 `wasmd keys show` 解析地址；
2. 与链上 `treasury_multisig {"signers":{}}` 返回的 5 个地址**逐一精确比对**；
3. 全部一致才允许删除；删除后立即 `shred` 掉中间副本。

> 这一步第一次跑是**失败**的，原因是我的校验脚本把 bech32 地址长度写死成 39 位
> （实际 `wasm1` 后是 38 位），导致正则永不匹配、误判"备份不可用"。
> 教训：**闸门报错时先怀疑闸门本身**，不能因为"闸门拦住了"就以为备份真的坏了——
> 反过来更危险：如果我把长度放宽成"能过就行"，就可能带着一个不可还原的备份删掉私钥。

## 今后要动用金库时的正确流程

前提：需要所有者提供 7z 密码与 openssl 口令（这是设计出来的摩擦，不是 bug）。
桌面 \ 里双击 \ 即可解出这两个文件。

```bash
# 1) 用口令解密到内存盘（tmpfs，不落磁盘）
mkdir -p /dev/shm/ldkeys && chmod 700 /dev/shm/ldkeys
read -s -p "口令: " P && openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -pass pass:"$P" -in /home/ubuntu/backup/treasury-keys-*/treasury_signers_keyring.tar.gz.enc \
  | tar xz -C /dev/shm/ldkeys && unset P

# 2) 用临时钥匙串发起/审批/执行（--home 指向 /dev/shm/ldkeys 的父级）
wasmd keys list --keyring-backend test --home /dev/shm/ldkeys
#   …… 正常执行 propose_transfer / approve / execute_transfer ……

# 3) 用完立刻销毁内存副本
find /dev/shm/ldkeys -type f -exec shred -u {} + ; rmdir -p /dev/shm/ldkeys/keyring-test 2>/dev/null

# 4) 事后必须做的三件事（硬规则）
#    a. 写 docs/TREASURY_MOVEMENT_LEDGER.md：提案号/签名人/时间锁到期/执行哈希/执行后余额
#    b. 执行前后各向所有者报告一次
#    c. 复跑 ld_monitor.py 与渲染巡检确认无副作用
```

## 事故记录：2026-10-16 摘除过程中发现的"加密备份内含明文私钥"缺陷

**发现方式**：摘除完成后，为验证"本机口令+密文能否解密"而在服务器做全盘清点时发现
`/home/ubuntu/backup/treasury-keys-20261015T072658Z/` 目录里，除密文外还并存
`keyring-test/signer1..5.info` 与 `verify/keyring-test/signer1..5.info` —— 共 10 个
**未加密私钥**（另有我调试产生的 `/tmp/dbg-restore/` 5 个，合计 15 个）。

**根因**：我 10-15 写的冷备份脚本 `ld_coldbackup_treasury_keys.sh` 把打包源目录和
解包验证目录都放在同一个 `treasury-keys-*` 目录里，且收尾没有清理。
后果：所谓"加密冷备份"旁边就摆着明文，加密形同虚设——拿到这台机器的人不需要口令。

**处置**：
1. 先确认这些副本解析出的 5 个地址与链上 `signers` 逐一一致（证明钥匙并未丢失）；
2. 用新口令重建 v2 备份：密文单独存放、口令只写内存盘、当场解密还原并逐把比对通过；
3. 把 v2 密文与口令分别交付到所有者本机，并**在所有者机器上实际解密成功**
   （本机与服务器密文 sha256 一致：`34e55ed487ae1856…`）；
4. 之后才 `shred` 掉服务器上全部 15 个明文、v1 密文（其口令已丢失不可解）与内存盘口令；
5. 独立复核：全盘 `signer*.info` = 0、钥匙串 signer 条目 = 0、备份目录无口令文件。

**新增不变量与检测点**：`/usr/local/bin/ld_treasury_keywatch.sh`（root cron 每小时 23 分）
监控四条：机器上不得有 `signer*.info`；钥匙串 signer 条目必须为 0；必须存在 v2 密文；
密文目录内不得有明文或与密文同机的口令。已双向验证：植入明文 → `VIOLATION` 且退出非 0；
清除后 → `OK` 不误报。备份脚本本身也已追加"收尾粉碎明文 + 调用该检测"的清理块。

**当前密钥态势**：
- 网关不再持有任何金库私钥（明文与口令都没有）
- 唯一可用备份 = 所有者手上的 v2 密文 + v2 口令（两者分离保管）
- 链上仍是 3/5 多签 + 72 小时时间锁，未做任何链上变更
- 资金复核：金库 842,000,093.16 LIGHT、生态基金 400,000,000.00 LIGHT，与摘除前一致

**遗留风险（重要，需所有者决策）**：私钥现在只有**一份**备份，且保护方式是"单个口令"。
口令丢失或两份文件同时损毁 = 金库永久不可动用（更换签名人本身需要 3/5 现有签名人投票）。
建议：口令至少两处独立保管（密码管理器 + 纸质），并尽快把 5 把钥分散到 5 台独立主机/硬件。
## 追加：2026-10-31 可核实性边界与副本实测（同轮由门禁触发，非人工发现）

### 1. 这份手册里有几句"我说的"，而不是"链上可查的"——必须标明

链上实测（任何人可在网关重跑）：

- `treasury_multisig` 的 query 接口**只有两个**变体：`tx` 与 `signers`。未知变体直接报错
  （实测传 `{"threshold":{}}` 返回 `unknown variant \`threshold\`, expected \`tx\` or \`signers\``）。
  → **阈值（本手册写 3/5）无法从链上查询自证**，它是当年部署记录里的数字。
- `{"signers":{}}` 返回 **5 个地址** —— 这一条是链上可查的，站内文案已改成只说这句。
- 实例化交易不可检索：本机 `wasmd q txs` 按高度分档抽样实测，`tx.height` 0–30 万命中 **0 笔**、
  30–40 万起才有命中（共 949 笔可查）；`message.action='/cosmwasm.wasm.v1.MsgInstantiateContract'`
  全库命中 **0 笔**。→ 想从链上直接证明"3/5"或"7 个授权账户"，需要一个归档节点或当年的部署日志。
- `{"tx":{"id":1}}` 返回字段 `amount/approvals/denom/executed/id/queued_at/recipient`，
  **没有** `execute_after`/`threshold` → 本手册写的"72 小时时间锁"同样属于"部署代码里的规则"，
  不是页面访客能一条命令查出来的东西。

结论：涉及金库对外说法时，只写"链上 5 个签名人（阈值未开放公开查询）"。
站内已于 v1.10.4/v1.10.5 按此口径改完（zh/en + 13 个译种，见 docs/PROPOSAL_DECISIONS.md 同日记录）。

口令至少两处独立保管（密码管理器 + 纸质各一，分放两地），并在方便时做一次"能否解密"演练。

### 3. 签名人不冗余这件事，为什么比文案错误更危险（本轮新发现，已确认有检测点）

每日贡献分根的链上事实（95 笔 `submit_root` 交易实测，天 31–49）：
`threshold` 全部为 **5**；实际参与签名的账户恰好 **5 个**（每把各 19 笔），每天投票数 1→2→3→4→5，
到第 5 票才 `committed=true`。也就是说：**5 把签名钥必须天天全在线**，少一把当日根就上不了链，
当日所有矿工都领不到奖励——不是"少一个人参与"，是"全链结算停摆"。

检测点已存在（不必新造门禁）：`qa_cross.py` 的 C2 会在
"网关已定稿（`/v1/day` finalized=true）但链上 `root_submitted` 为 false" 超过 6 小时后
打 `MISSING-OLD` 并非零退出 → 告警进 `/home/ubuntu/ld_alerts.log`。
白皮书设计的"7 个授权账户"若真实存在（即还有 2 把备用钥），当前观测里**没人用过**，
这层冗余到底是"有但没用上"还是"根本没有"，需要所有者确认部署记录后我才能把站内说法恢复成分母形式。
