# SRI 告警排障记录（2026-11-05 ~ 11-06）

> 触发：整点巡检发现 `ld_alerts.log` 里 3 条 `SRI-MISMATCH`（11-05T06:33Z / 11-05T18:33Z / 11-06T00:33Z），
> 而 11-06 白天各次校验都是 `fails=0`。要求"不许只转述"，故定位到根因再记录。

## 结论：不是量具误报，是真实的瞬态不一致；当前已收敛

| 时刻(UTC) | checked | fails | 现状 |
|---|---|---|---|
| 2026-11-05T06:33 | 648 | 144 | 之后自愈 |
| 2026-11-05T18:33 | 648 | 144 | 之后自愈 |
| 2026-11-06T00:33 | 648 | 144 | 之后自愈 |
| 2026-11-06T03:30 / 06:33 / 12:33 / 14:09 | 648 | **0** | 通过 |

144 = 18 个 HTML × 8 个 `i18n_mt_*.js`。FAIL 明细全部落在 `/js/i18n_mt_N.js` 的 `hash-mismatch`，
不涉及 vendor 脚本，即**不是白屏级全站故障面**，而是翻译分片这一条链路。

## 根因（调度设计缺陷，非生产数据错误）

多语言批量任务每分钟 :30 跑（`LD_BATCH=45`，root crontab），它会重写
`/var/www/lightdao/js/i18n_mt_1..8.js`；而 SRI 校验固定在 :33 跑（`33 */6 * * * # LD-SRI`）。
分片内容变了、HTML 里的 `integrity` 属性要等另一条注入/渲染链路（`ld_render_truth.py render` 06:40、
`static` 每 6h :35）才更新。于是 :30→注入完成之间存在一个真实的不一致窗口，:33 恰好踩在里面就报 144。
下一次非 :33 的校验（03:30）自然就是 0。

**为什么 11-06 只有 00:33 中招**：当天 :30 批次输出 `本批成功 0 失败 0`，但分片文件仍被重写
（`i18n_mt_1.js` mtime=14:00:21Z，即每个 :30 都在 touch）。只有内容确有变化的那批才会造成 hash 落后。

## 顺带发现的两个观测性缺陷（建议，未动手）

1. **`ld_sri_cron.log` 是个空文件诱饵。** cron 行把输出重定向到 `ld_sri_cron.log`，
   而脚本内部 `LOG=/home/ubuntu/ld_sri.log` 自己写结果。所以 `ld_sri_cron.log` mtime 停在 10-30、
   大小 0 字节，按"日志 mtime 判哨兵死活"会误判成哑掉；真正的心跳在 `ld_sri.log`。
2. **两条 cron 都调 `ld_sri.sh`，输出被截断。** `30 3 * * *`（无 `>>`，且未登记在 manifest）会把
   `ld_sri.log` 整份截断。11-06T00:33 那次报警的 FAIL 明细正是被 03:30 这次截断吃掉的——
   夜间告警的证据留存不下来。修法方向：统一成一个写 `ld_sri.log` 的追加调用点，或让脚本自己带日期。

## 判据本身的一个坑（排障过程中踩到，值得写下来）

`ld_sri.sh` 里 `alert()` 的文本是追加写入 `ld_alerts.log`，**不带 `ALERT` 前缀**；
巡检用 `grep ALERT` 统计告警数会系统性漏掉 SRI-MISMATCH / SRI-TOOL-BAD 这类。
另外脚本取结果行用 `echo "$OUT" | tail -1`，而工具是先打 FAIL 明细、最后打汇总行，
所以读 `ld_sri.log` 时**汇总行在 verdict 之后**（属于下一轮），按行号往下读会张冠李戴。
