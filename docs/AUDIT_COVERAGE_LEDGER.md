# 审计覆盖账本与方法附录(AUDIT COVERAGE LEDGER & METHODS APPENDIX)

本文件是 `AUDIT_PROGRAM.md` 的**方法论附录**,只含通用审计方法、登记表模板与证据卫生规则。
**不含任何具体系统的实时弱点、地址、密钥或数值**——那些只存于服务器私有 `OPS_ROADMAP`。
公开仓库仅保留可复用的方法,使任何审计者可按同一标准复核,而不泄露被测系统的当前缺陷。

## 1. 六元组不变量登记表(模板)

每条系统不变量按下表登记;缺任一列即视为"未审计"。

| 不变量 | 层 | 执行点 | 检测点 | 告警 | 测试 | 状态 |
|---|---|---|---|---|---|---|
| 用一句话写"必须恒成立的性质" | 客户端/网关/合约/链/运维 | 谁在运行时强制它(代码路径/配置) | 谁独立复核它(对账/探针/查询) | 违反时谁通知人(渠道) | 哪个测试/演练证明它(可复跑) | 已证 / 缺口 / 接受风险+理由 |

**状态词汇**:
- `已证` = 执行点+检测点+告警+测试四者齐备且同层,并有可复跑证据。
- `缺口` = 四者任一缺失;必须附排期与负责窗口。
- `接受风险+理由` = 明确书面接受,附理由与复评日期。

**同层原则**:执行点与检测点必须在同一层可互相印证(例如"链上承诺"必须由"独立重算链上原始输入"来检测,而非由产生该承诺的同一组件自报)。

## 2. 独立 oracle 重算方法(经济对账核心)

原则:**绝不信任被测系统对自身的报告**。对任何"承诺值"(如 Merkle 根、聚合分、总供应),从**原始输入**独立重算并与承诺比对。

通用步骤(以"每日贡献承诺"类系统为例):
1. 取**原始 leaves**(每个参与者的维度计数),不取系统已算好的聚合。
2. 按**公开、固定的编码规则**重算叶子哈希:定宽字段(如 `day` 用 u64 小端、各维度用 u128 小端)+ 变长但字符集受限的标识(如 bech32 地址)。**定宽编码消除长度歧义**,使两个不同 `(标识, 维度)` 元组不可能产生同一 preimage;叶子输入长度 ≠ 内部节点输入长度(如 `sha256(left32||right32)` 的 64 字节),**消除叶/内部节点碰撞**。
3. 重算树根(奇数复制末节点规则须与实现一致),与系统自报根、以及**链上承诺**三方比对。
4. 重算聚合分(各叶加权和),与自报值比对。
5. 逐条验证系统签发的证明(proof)对重算根成立(`bad_proofs == 0`)。
6. 任何不等 → 告警 + 阻断结算。

**供应守恒**(独立 oracle):从链**原始事件**(mint/claim/burn/transfer)重算 `Σmint − Σburn == 流通`,并与"总供应查询"和"账本 denom 语义"交叉核对;警惕**denom 脑裂**(铸计 denom ≠ 质押/计价 denom)造成的守恒假象。

**部署码 vs 源码**:核对每个已部署字节码的哈希可由仓库某 commit **可复现构建**得出;若线上查询面/存储命名空间与仓库 HEAD 不一致,即"部署≠源码"缺口,须登记。

## 3. 对抗性检查清单(通用,非本系统特定)

按"我会怎么攻击 / 什么会静默失效"逐条过(方法层面,公开无妨):
- **手续费代付/授权(feegrant 类)**:授权是否限定 `allowed_messages`?最坏 granter 燃烧 = Σ spend_limit?granter 是否为高值热钥?
- **反女巫**:计分输入是否客户端自报、无 PoW/无签名?固定池下农场能否稀释诚实参与者?每-IP 上限是否只限"发放"而不限"计分"?是否按精确 IP 串计数(IPv6 前缀轮换即破)?IP 归属是否可能塌缩到单一值?
- **治理完整性**:`execute` 是否有授权与过期?已通过未执行的提案是否可被任意人随时触发?竞争性迁移提案是否互斥?投票权是否依赖当前已坏的前置(如质押)?编号体系(链级 x/gov vs 合约内)是否混用?窗口排序是否安全?
- **客户端托管**:种子/私钥在何处驻留(会话存储明文?加密 at-rest?KDF 迭代数?)?登出是否真正清除?敏感操作是否有 step-up?社交恢复份额的合谋阈值?
- **可用性/DR**:证书/域名到期与自动续期?备份是否**真恢复演练一次**(恢复到临时目录验可读,不碰生产)?备份范围是否含密钥与共识状态?日志是否轮转?监控自身被致盲(日志/告警汇不可写)时是否**静默**?回滚快照是否==真·上一版?cron/计划任务的**时区**是否与意图一致(守护进程是否在 TZ 变更后重启)?
- **Web/供应链**:CSP/HSTS/X-Frame-Options 是否齐备?第三方 CDN 依赖是否有 SRI 或纯自托管?动态 `import()` 无法加 SRI——是否有 CSP `script-src` 兜底?收益类文案是否有等显著、**多语言**的免责声明?
- **完整性清单(SRI 类)自身可信性**(易被"已建门"谎报):①清单是否在改资源的**同一 commit/部署**内重生成?(清单 mtime 早于资源 mtime = 陈旧,门会静默变红)②清单里是否有**多个不同文件共用同一哈希**?不同内容不可能同 sha,共用即**占位/伪造**,该门并未真正校验任何东西。③完整性是否在**交付层强制**(HTML `<script integrity=>`),还是只有一个旁路校验脚本?(旁路脚本即使全绿,浏览器也不拦截被替换的资源)④校验**失败是否告警并阻断发布**?只 `>> log` 而无人消费 = 失败静默(等同没有门)。结论:凡"清单陈旧 / 占位重复 / 未强制 / 失败不告警"任一成立,该 SRI 门不计入"已建门"。
- **门/监控自身的确定性(run-context 无关)**:配置漂移门、清单核对门等若采集"调用者上下文"(如 `crontab -l` 取的是**运行身份**的 crontab,而非目标 root crontab),会出现**同一时刻不同身份给出相反判定**(服务身份=DRIFT、sudo=clean)→ 门不可信。修法:显式采集目标身份(如 `crontab -l -u root`),并对**未 ack 的漂移告警**跟踪到闭环(要么审查后 ack 重基线、要么回滚),不允许"报了漂移但无人处置"长期悬挂。同一 bug 常在一处已修、他处遗漏——修一个门时应全局搜同类采集模式。
- **头部可信性**:网关是否无条件信任 `X-Forwarded-For`?边缘代理是否覆写而非追加?直连内部端口能否绕过头部覆写?

## 4. 行动分桶(交付物标准分类)

每条发现归入下列桶之一(便于排期与问责):
- **(i) 需停机/维护窗口**:主机或共识相邻变更(密钥迁移、守护重启、快照重拍)。
- **(ii) 需治理提案**:链上参数/合约迁移/经济规则变更(经 x/gov 或合约治理)。
- **(iii) 需代码发布**:前端/网关/合约的常规发布管线变更。
- **(iv) 接受风险+理由**:书面接受,附理由与复评日期。

## 5. 覆盖账本要求

每次全量审计必须对**每一类审计**(见 `AUDIT_PROGRAM.md` §1 的 8 类)给出:≥1 条发现,**或**一行显式"由 X 覆盖,无缺口"(注明覆盖它的测试/演练/cron)。缺口不可见 = 审计失败(反例库第 7 条)。

## 6. 证据卫生规则(硬约束)

- 主网默认**只读**;唯一例外=从自有 canary 钱包发"故意失败"的探测 tx。
- 不做验证者密钥操作、不重启、不改主网配置;破坏性演练只在 testnet/staging。
- **公开仓库只放脱敏方法论**(本文件即范例);实时弱点、地址、密钥、可被利用的数值只存服务器私有 `OPS_ROADMAP`,永不入 git。
- 每条发现附:严重度 + 证据命令/输出 + 修复 + 六元组 + "今天是否有检测"。
- 编辑 root 属主的 web 文件经"本地改 + scp + sudo",不用内联 heredoc。
