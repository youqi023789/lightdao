## 提案 #11：把挖矿日界对齐到 00:00 UTC —— 决定：不执行（让它到期作废）

- 内容：`migrate` 目标合约 `mining_reward`（`wasm173y0p…r9wx`）到 **code 15**，
  并带 `call_msg = {"new_genesis_time": 1789084800}`（= 2026-09-11 00:00:00 UTC）。
- 投票：ptype `major`，赞成 7,000 LIGHT（1 个地址）、反对 0、弃权 0；投票截止 2026-10-18 15:41 UTC。
- 提案自身到期：**2026-11-01 16:41 UTC**（过期后合约判 expired，不可再执行，也不占用 C7）。
- 决定时间与决定人：2026-10-31，创始人（用户）在给出建议后确认"继续"，采纳"不执行"。

### 为什么不执行（三条都是实测，不是感觉）

1. **不执行也没有用户受损**：网关 `gateway_v3.py` 早已自己做 00:00 UTC 对齐
   （`CUTOVER` / `D_CUT` 逻辑，注释里明确写了"首个 00:00 对齐天 = +1，防索引碰撞"），
   跨层自检 C1"纪元偏移"当前实测 offset=0 通过；每日 finalize、领取根提交、
   金丝雀模拟领取（day 48 实测 delta 88,492.24 LIGHT，tx code=0）都在正常走。
2. **迁移目标是不可复现的字节码**：`contracts/wasm/BUILDLOG.tsv` 里 code 15
   `reproducible=no`、`source_commit=unknown`（字节码是 2026-10-16 从节点 wasm 存储回捞的，
   跟踪例外解除日 2026-11-30）。把领取校验的地基换到一个我们讲不出源码的字节码上，
   正是我自己那道 migrate 门禁要拦的事。
3. **改纪元起点会移动合约侧的天索引**：合约是按天索引校验 Merkle 根与领取窗口的，
   已上链的每日根（第 1–49 天）索引不动、合约基准一动，边界附近的领取存在被判无效的风险。
   收益（少一处"两套事实源"）明显小于这个风险。

### 复核条件（什么时候该重新提）

同时满足以下两条再重新提案：

- code 15（或其后继版本）的**源码与工具链能讲清楚**：`contracts/contracts/` 下有对应 crate，
  CI 能按配方复现出与链上一致的 sha256；
- 在**测试链**上完整验证一次"跨纪元起点改变"的场景：改前一日、改当日、改后一日的
  根提交与领取都必须 code=0，且旧天索引不被误认。

在那之前，"网关对齐、合约未对齐"这个不对称由本文件记录在案，
C7 不再重复报警，但每日巡检仍会显示 `decided=[11]`，便于随时复核。

## 2026-11-04 GitHub 推送通道偶发抖动（实测），已加重试与"卡住必须响"

现象（同一台网关、同一把 ed25519 部署密钥，几分钟内）：
`ssh -T git@github.com` 6 秒内 2 次成功 + 1 次 `Permission denied (publickey)`；
`git push` 连续 4 次失败、第 5 次成功；后来 `ld_push.sh` 也是第 3 次才成。
所以这**不是**密钥被撤销（撤销会一直失败，而且 `git ls-remote` 也会一直 128），
而是 GitHub 侧偶发拒绝——我一度按"密钥被撤"去查权限，用外部事实（推文 snowflake 时间戳、
API 里仓库仍 public 且 pushed_at 在推进）才把误判纠正回来。

真正的风险不是"这一次失败"，而是"以后失败时没人重试、也没人发现"：
站内承诺"合约开源、可自验"，访客是照着 GitHub 仓库核对的；提交只要停在本机，这句话就不成立。

已做的三件事（都有反向验证）：
1. `qa_cross.py` 新增 **C8**：本地 HEAD 必须已推到 origin（`rev-list --count @{u}..HEAD == 0`）；
   取不到远端/输出不是数字一律 FAIL。实测：`LD_REPO_REF=refs/heads/nope-timeout-test` → `FAIL C8`。
   这是"每小时会响一次"的检测点，仓库落后不会超过一小时没人知道。
2. 新增 `/usr/local/bin/ld_push.sh`：推送最多重试 5 次（退避 15/30/45…），
   结束后客观核对 gap；没追平写 `REPO-PUSH-STUCK` 告警并 exit 5。
   实测正向 "第 3 次成功、gap=0"；反向（指向不存在的仓库）rc=5 且告警落盘。
3. `ld_cfg.sh ack` 重新基线：本轮 5 处 cron 变更（摘掉两条营销任务的 `DRY_RUN=1` 前缀 +
   新增 ld_render_truth static/render、ld_x_cred_probe 三条）逐行核对都是我自己的授权改动，
   现在 `config clean`。

一处自我更正（写下来防止以后误读历史）：10-31 我根据日志得出"每日帖自 10-24 起 14 次全在 DRY 空转、
一条都没发出"。那是**当时**的正确结论（DRY 前缀确实在 crontab 里，10-31 08:44Z 才摘掉）；
之后从 10-31 16:30 到 11-04 04:30 共 8 个槽位：**7 次真实发出、1 次失败**
（2026-11-02 04:30:04Z `X-POST-FAIL rc=1 slot=am n=7`，是刚加的发帖失败告警在真实环境里第一次响）。
每条都用推文 ID 内嵌的时间戳（外部权威时钟，不受本机时钟影响）核对过发出时刻。

顺带补掉一个刚暴露的缺口：那条 11-02 的告警只有 `rc=1` 和"凭据失效/额度/网络"三个猜测，
发帖器真正的报错被吞掉了，事后无法判断到底是哪一种——**告警不带原因就等于把排查推给下一个看日志的人（就是我）**。
现在发帖输出会留末 6 行进 `ld_x_mkt.log`，并把末行摘要塞进告警文本
（实测注入桩输出 "媒体上传失败 HTTP=503 upstream-temporary" → 告警里原样带出）。
返回码改用 `POST_RC`，不是管道的 `$?`（管道尾是 tail，恒 0，会把失败读成成功）。

## 2026-11-04（同日续）金库阈值按所有者裁定收敛为 3/5，并发现两批钥匙互不相同

所有者裁定：**金库阈值以白皮书为准**；并说明"之前只给了 5 把密钥签名让我保存"。

链上/文档实测（四条都是本轮查的，不是回忆）：
1. `treasury_multisig {"signers":{}}` 返回 **5 个地址**；该合约只有 `tx`/`signers` 两个查询，
   **阈值本身不在查询接口里**，实例化交易在本节点交易索引中检索不到。
2. 白皮书自己前后矛盾：正文 §7.2/§7.3 与 §8.1 写 **3/5**（§8.1 还把分子分母写成"多签5/3"），
   而自称"主网**已验证**参数与地址"的附录却写 `treasury_multisig` 是 **5/7**。
   5/7 需要 7 名签名人，链上没有；3/5 与链上 5 名签名人自洽 →
   按"以白皮书为准"取正文的制度设计 **3/5**，附录那句按笔误勘误（不动版本号，只加带日期的勘误条目）。
3. **新实测**：金库的 5 个签名地址与每日挖矿根的 5 个签名账户**交集为 0**，是两批完全不同的钥匙。
   所以风险要分开说：丢一把**金库**钥匙只是审批弹性下降（4 人里凑 3 票仍可动，但更换签名人本身要 3/5 现有签名人投票）；
   丢一把**结算**钥匙当日上链只有 4 票、达不到阈值 5，**当天所有矿工领不到**
   （检测点 `qa_cross.py` C2：网关已定稿而链上无根超 6 小时 → MISSING-OLD 报警）。
   我在 10-31 的手册里笼统写过"少一把当日结算就停摆"，没区分两批钥匙，会让人把风险错估到金库那 5 把上——已更正。
4. 挖矿根侧继续按"分子可证就说分子"：阈值 5（115 笔 `submit_root` 事件实测全部 threshold=5），
   "7 席授权"是设计目标、当前无链上证据，附录相应改写。

站内措辞（v1.10.9）：三处金库说法统一为"3/5 多签（白皮书 §8.1）· 链上 5 个签名人可查，
阈值本身不在查询接口内"，中英文 + 13 个语种译值一起带上语言中立的 `3/5`。
本轮把正向校验补上之后才发现：**只查"旧词是否消失"永远发现不了"某个语种压根没被规则命中"**——
第一次正向校验就抓出两类漏网（菲律宾语是 `5-signature multisig`、西/葡/印尼/越是 `5 firmas del tesoro`
这种数字开头的写法），补齐后逐语种确认 14 个值都带 `3/5`，16 条渲染用例全过。

顺带抓到并修掉一个真正的双源漂移：**白皮书线上是旧版**。
`promote.py` 只复制 `*.html` 与 `js/*.js`，`whitepaper.md` 从来没被它带上去，只能手工 cp——
今天加完勘误后我用 `curl https://lightdao.net/whitepaper.md` 与仓库 md5 一比，才发现两份表达不一致
（线上 92fbc932…、仓库 9cc2b7ae…），手工复制后才一致。也就是说"改了就等于发布了"这句话对白皮书根本不成立。
两处收口：
- 新执行点 `/usr/local/bin/ld_asset_sync.sh`（root cron `45 5 * * *`，清单 65 条已对账）：
  白名单式按内容比对同步（不用通配，线上 html/js 带 SRI 注入必须走门禁，不能被它绕过覆盖），
  复制后回读比对，源文件读不到=失败并报警。反向验证实测：源目录不存在 → rc=5 + `ASSET-SYNC-FAIL` 落盘；
  指向空目标目录 → 真复制且哈希一致；已一致 → 不动作。

  反向验证：临时站根放一份内容不同的白皮书 → `FAIL 线上 whitepaper.md 与仓库不一致（live=… repo=…）`；
